# Reflection 1 — Plan vs. Reality

The largest gap between the original plan and the finished data model was the rating type. Plan section 3 says restaurant ratings are integers from 1 to 5. The actual five primary restaurant ratings supplied for the journal were 4.6, 4.5, 3.6, 4.2, and 4.3. An integer-only field would have discarded information or changed those values by rounding. Their sum is 21.2; divided by five, the average is 4.24, which the dashboard displays as 4.2.

The responsibility for this change was shared. The owner supplied the five actual decimal ratings as task data. The coordinating assistant noticed those values did not fit the integer-only field in Plan section 3 and converted that mismatch into the technical instruction recorded in `prompts/data-model.md`: “Rating CHANGE requested from actual user entries: accept one decimal 1.0–5.0, rather than the original integer plan.” Replit Agent implemented that requirement. The agent-authored Plan-deviation response in the same log says: “The original plan sections were left untouched; PostgreSQL enforces the requested range and one-decimal increments.” The owner accepted the implementation through the supplied data and delegated task, but did not independently choose the PostgreSQL type or constraint. This separates the owner’s role in supplying and accepting the work from the coordinating assistant’s requirement translation and the Replit Agent’s technical implementation.

The implementation uses PostgreSQL `numeric` and a check constraint that accepts `NULL` or a value from 1.0 to 5.0 in tenths. Client and server validation use the same range and precision. This prevents the database from quietly accepting a value such as 4.56 when the interface supports only tenths. A blank rating remains `NULL`, not zero; zero is not a valid rating. Those details matter because a restaurant without a rating is different from a restaurant rated at the bottom of the scale.

The implementation cost was cross-layer: the migration and database constraint, client and server validation, form, dashboard aggregation, and regression tests all had to agree. This took more work than changing an integer column to `numeric`, but it prevents different layers from accepting or displaying different values. The dashboard averages only non-null ratings belonging to the signed-in owner and rounds to one decimal. Its required test uses two accounts and an unrated entry to verify that ratings 5 and 3 produce 4.0, excluding both the blank rating and the other account. The isolation test separately checks that another account cannot see or change an owner’s restaurant.

A fresh-agent requirement should state: “Store optional ratings as PostgreSQL numeric tenths from 1.0 to 5.0. Store blank as `NULL`; reject finer precision rather than rounding. Calculate averages only from the current owner’s non-null ratings, and preserve the original Plan text.” The plan remains intact so this difference is visible, while the schema documentation explains the implemented rule. The lesson is to compare a proposed model with realistic values and preserve a traceable handoff: the owner supplied the data and delegated the task, the coordinating assistant translated the mismatch into a precise requirement, and Replit Agent implemented the database and application rules. The owner accepted that implementation without independently selecting the SQL design.
